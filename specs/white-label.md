# White-label: один репо → N магазинів

**Модель:** одна кодова база, кожен магазин = окремий деплой (свій домен, своя БД, свій theme-файл і seed).
**Редагування контенту:** клієнт через адмінку (тексти, контакти, оплата/доставка, бренд).
**Одиниці виміру:** фіксований список фасувань на магазин (у налаштуваннях, не в коді).

Ніякого `TenantId` у коді — ізоляція на рівні деплою. Це прибирає найбільший ризик
мультитенанту (витік даних між магазинами) і не заважає фіксам розходитися по всіх сайтах.

## 5 шарів відмінностей

### 1. Кольорова гама → семантичні токени (найбільший борг)

**Стан зараз:** у `frontend/src` — **694** посилання на літеральні назви палітри
(`--espresso-900`, `--marigold-400`, `--kraft-100`, `--cinnamon-700`, `--chili-500`, `--garden-700`)
проти лише **241** семантичного (`--text-body`, `--bg-page`, `--border-subtle`) — по 36 шаблонах.
Перетемувати сьогодні = find/replace у 694 місцях, і назва `espresso` нічого не означає
для магазину чаю чи косметики.

**Рішення:** шаблони посилаються **тільки** на семантичні токени. Палітра живе лише у theme-файлі.

`src/themes/_tokens.css` — контракт (перелік імен, без значень):

| Група | Токени |
|---|---|
| Поверхні | `--bg-page`, `--surface-card`, `--surface-muted`, `--surface-inverse` |
| Текст | `--text-strong`, `--text-body`, `--text-muted`, `--text-on-accent` |
| Акцент | `--accent`, `--accent-hover`, `--accent-strong`, `--accent-subtle` |
| Другорядний | `--secondary`, `--secondary-strong`, `--secondary-subtle` |
| Стани | `--danger`, `--danger-subtle`, `--success`, `--warning` |
| Межі | `--border-subtle`, `--border-strong` |
| Шрифти | `--font-display`, `--font-body`, `--font-accent` |
| Геометрія | `--radius-sm…xl`, `--shadow-xs/md/lg/focus` |

Геометрію теж винести: спеції = теплі великі радіуси, косметика = різкіші й мінімалістичні.

`src/themes/fayno-spices.css` — палітра + маплення. Таблиця міграції:

```
--espresso-900 → --text-strong        --marigold-400 → --accent
--espresso-800 → --text-body          --marigold-500 → --accent-hover
--espresso-700 → --text-body (soft)   --marigold-100 → --accent-subtle
--kraft-500    → --text-muted         --cinnamon-700 → --accent-strong
--kraft-50     → --bg-page            --chili-500/700 → --danger / --danger-strong
--kraft-100    → --surface-muted      --garden-500/700 → --secondary / --secondary-strong
--kraft-300/400 → --border-subtle / --border-strong
```

**Захист від регресу:** stylelint-правило або grep-крок у CI, що падає, якщо в `src/app/**`
з'явився літеральний токен палітри. Без цього борг відростає за два спринти.

Крок 1 — чистий refactor: тема Файно має виглядати піксель-в-піксель так само.

### 2. Тексти сторінок → ContentBlock у БД

**Стан зараз:** сторінки `about`, `payment-delivery`, `contacts` — 100% на transloco-ключах
(`about.*` ≈ 6 КБ, `paymentDelivery.*` ≈ 4 КБ, `contacts.*`). Це дуже добре:
розмітку **не треба переписувати**, змінюється лише джерело значень.

**Рішення:** два словники, що зливаються.

- `public/i18n/{ua,en}.json` — **словник коду** (кнопки, валідація, лейбли). Зона розробника, лишається у git.
- `GET /api/content/{lang}` — **редагований словник** (namespaces `brand`, `seo`, `about`,
  `paymentDelivery`, `contacts`). Зона клієнта, живе в БД.

`AppTranslocoLoader.getTranslation(lang)` тягне обидва і робить deep-merge; JSON з коду —
fallback, якщо ключа в БД немає. Так нові ключі, додані в коді, працюють до того,
як хтось відкриє адмінку.

- **SSR:** фетч на сервері + `TransferState`, щоб не було миготіння й SEO не втратив текст.
- **Кеш:** ETag + короткий TTL, інвалідація на save в адмінці.

```
ContentBlock { Id, Key ("about.mission.body"), Lang, Value, UpdatedAt }
UNIQUE (Key, Lang)
```

Адмінка: редактор, згрупований за namespace, rich-text для довгих полів, preview.

### 3. Конфіг магазину → розширений ShopSettings

`ShopSettings` зараз singleton з одним полем (`UkrposhtaFreeFromAmount`). Це природне місце
для всього, що відрізняє магазин:

- **Бренд:** name, legalName, logo, favicon, ogImage, themeId
- **Контакти** (структуровані, не вільний текст — бо йдуть у JSON-LD, футер, чекаут):
  phone, contactPerson, region, city, place, mapEmbedUrl, hours (online / shop), соцмережі
- **Доставка:** список активних методів, поріг безкоштовної доставки на метод, адреса самовивозу
- **Оплата:** список активних методів, текст інструкції
- **Одиниці:** дозволений список фасувань (див. §4)
- **Аналітика:** GA / Meta pixel id, Telegram chat id

`Constants/DeliveryMethods.cs` і валідація чекауту мають читати список з налаштувань, а не з констант.

**Секрети — тільки env, ніколи в БД:** `Jwt__Key`, `Resend__ApiToken`, `NovaPoshta__ApiKey`,
`Telegram__BotToken`, `ConnectionStrings__DefaultConnection`.

`environment.production.ts` зараз хардкодить `apiBaseUrl` і `siteOrigin` → перевести на
build-time змінні, щоб один репо збирав N сайтів без правок файлів.

### 4. Одиниці виміру → код + список у налаштуваннях

**Стан зараз — три джерела правди:**
`backend/Constants/PredefinedWeights.cs`, `frontend/src/app/models/admin.models.ts` (дубль),
плюс захардкоджений український текст помилки у `ProductService.cs:473` і
`SaveProductRequestValidator.cs:58`. Сам `WeightUnit` — це **рядок для показу** (`"г"`, `"кг"`, `"шт"`),
через що EN-локаль показує кирилицю, а сортування залежить від тексту.

**Рішення:**
1. `WeightUnit` стає кодом: `g` | `kg` | `pcs` | `ml` | `l` (+ `cm`, `pack` за потреби).
   Показ — через i18n (`unit.g` → «г» / «g»). Міграція мапить наявні рядки.
2. Дозволений список фасувань переїжджає в `ShopSettings` (JSON):
   `[{ "value": 10, "unit": "g", "sortOrder": 1 }, …]`.
   Один source of truth: API віддає його, адмінка фетчить замість власної константи,
   валідатор перевіряє по ньому, текст помилки генерується зі списку.
3. Приклади наборів: спеції — 10/50/100/250/500 г, 1 кг, 1 шт; книги — шт;
   напої — 0.33/0.5/1 л; косметика — 30/50/100 мл.

Знімки в `OrderItem` (`Weight`, `WeightUnit`) лишаються як є — але теж у кодах.

### 5. Що НЕ параметризувати

Каталог, кошик, чекаут, auth, замовлення, новини, адмінка — однакові для всіх сайтів.
Якщо магазину потрібен принципово інший флоу — це сигнал на окремий продукт,
а не на ще один `if (shopId == …)`. Прапорці «на магазин» у бізнес-логіці — головний
спосіб убити спільну кодову базу.

## Структура репо

```
backend/                     ← спільний, без змін у структурі
frontend/
  src/themes/
    _tokens.css              ← семантичний контракт (імена, без значень)
    fayno-spices.css         ← палітра + маплення
    <next-shop>.css
  src/app/                   ← тільки семантичні токени
sites/
  fayno/
    site.json                ← бренд, домен, theme, набір фасувань
    logo.svg  favicon.ico  og.png
    seed.sql                 ← початкові ShopSettings + ContentBlock
  <next-shop>/
```

Збірка: `THEME=fayno-spices npm run build` (через `fileReplacements` в `angular.json`
або підміну css-entry). Контент і налаштування — зі seed тієї БД.

## Порядок робіт

Кожен крок — deployable, магазин Файно працює після кожного.

| # | Крок | Обсяг | Чому саме тут |
|---|------|-------|---------------|
| 1 | Семантичні токени + CI-lint | великий | Чистий refactor. Поки не зроблено — кожен новий сайт множить 694 місця. |
| 2 | `WeightUnit` → код, список у ShopSettings | середній | Потребує міграції БД; чим більше даних, тим дорожче. |
| 3 | Розширений ShopSettings + адмінка налаштувань | великий | Дає бренд/контакти/доставку/оплату без коду. |
| 4 | ContentBlock + API + merge у transloco + SSR | середній | Розмітка сторінок уже готова, лишається джерело. |
| 5 | Build-time env + `sites/<name>` | малий | Після цього другий магазин = тема + seed, без коду. |

**Кроки 1 і 2 варто закрити до старту другого магазину.** Кроки 3–5 можна робити паралельно
з першим клоном, але 1 і 2 — це саме той борг, що дублюється на кожен сайт.

## Відкриті питання

- Валюта й локаль: усі магазини UAH/uk-en, чи буде щось інше? (впливає на формати й на `Price`)
- Один Postgres-інстанс з N базами чи N інстансів? (перше дешевше на старті)
- Спільна адмінка «над» магазинами (список сайтів, здоров'я, замовлення) — потрібна чи ні?
- Юридичні сторінки (оферта, політика) — теж ContentBlock, чи окремий шаблон з підстановками?
